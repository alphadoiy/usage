# Provider 与模型性能

首页选中 Provider 看板后按 `v`，查看当前 Provider 的本地请求性能。弹窗固定绑定打开时的 Provider 与账号版本，较早任务的结果不会覆盖新弹窗。

首页 Provider 展示近 24 小时已索引请求的平均首字、生成速度及速度下限，各自标注有效样本数。计算对齐 Magpie 本地会话日志的 `MeanTTFT`、`Row.Decode` 和 `Row.Floor`：首字按有效请求求算术平均（毫秒取整），速度按各自样本的总 Token / 总有效时间加权，不平均每条请求的速度或模型均值。首页摘要按绑定缓存 5 分钟，左右切换直接复用；读取时只执行一条索引聚合，不扫描日志、不创建数据库。尚未建立索引时提示按 `v` 更新。弹窗完成索引后同步首页摘要；其他时间范围更新后，返回首页重新查询近 24 小时摘要。首页摘要允许延迟，不表示实时测速。

| 操作 | 作用 |
| --- | --- |
| `←` / `→` | 最近 24 小时、7 天、30 天 |
| `↑` / `↓` | 选择模型；明细中滚动 |
| `Enter` | 该模型的请求明细 |
| `PgUp` / `PgDn` | 明细翻页，每页最多 40 条 |
| `r` | 更新增量并重新发现日志文件 |
| `Esc` | 明细返回模型列表，或关闭弹窗 |

## 绑定与数据口径

托管 Codex 自动使用当前保存版本的 Home；OAuth 使用该账号的 Home，仅统计会话日志，不合并历史网关记录，也不因历史网关启动范围排除日志样本。模型取自日志中观察到的模型，不用配置的默认模型补齐。BYOK 日志的 `model_provider` 与保存版本不符，或模型缺失时，进入未归属计数，不计入模型统计。

独立 API Provider 需要显式指定专用日志实例，不回退到默认 `~/.codex` 或 `~/.claude`。在原有资源连接中增加 `inference.performance_instance`，指向 `[[instances]]` 的 ID。例如：

```toml
[[instances]]
id = "work-claude"
provider = "claude"
path = "/Users/you/.claude-work"

[[resources]]
id = "work-relay"
service = "new_api_token"
base_url = "https://relay.example"
credential_env = "RELAY_KEY"
[resources.inference]
base_url = "https://relay.example/v1"
credential_env = "RELAY_KEY"
performance_instance = "work-claude"
```

该目录需要专门用于此 Provider。显式目录绑定和日志里的提供方字段仅是关联证据，不能证明某次 HTTP 请求实际命中了哪个端点；共用 Home 的不同 Provider 不应拿同一批日志作端点速度对比。目前支持 Codex 和 Claude Code 日志，其他 Agent 需提供性能日志解析能力。

每个模型分别展示请求数、平均首字延迟、生成速度、速度下限，以及每项有效样本数。空缺显示 `—`，不当作 0。最多展示 500 个模型，超过上限时提示缩小时间范围。

- Codex 逐请求计时（对齐 cc-switch 与 Codex 源码）：新版 Codex 在响应结束时写入 `token_usage_record`，以它的时间作为该请求的结束；首字取本次请求内第一个回答项（`item_completed` 中 AgentMessage）的 `started_at_ms`，与 Codex 自身 `time_to_first_token_ms` 的口径一致。推理项整块写入（开始等于结束）、常晚于回答开始，不作为首字；只有工具调用的响应首字保持未知。Codex 在每次采样尝试结束时写 `token_count`，未带来新用量的 `token_count` 表示该尝试失败（如流超时后重试），下一次尝试从它开始计时。请求身份仍沿用 `token_count`，已有索引升级后按批重读并原位更新。
- Codex 旧日志：只有一轮恰好一个调用、完成事件的 turn ID 匹配时，才把 `task_complete` 的原生耗时和首字计时归给该请求；已有逐请求记录的请求不再用整轮计时覆盖。多调用轮次不复制同一个首字计时到每个调用。较早日志在工具执行后才写用量记录时，使用模型开始输出前的输入时间与对应输出时间，避免把工具执行误当作模型耗时，或把请求误算为几毫秒。
- Claude Code：按消息 ID 合并片段，从父链定位请求起点并跳过 attachment。与 Magpie 的本地日志读取一致，不从 thinking 块、`thinkingDurationMs` 或最终文本时间推算首字；缺少明确计时就显示 `—`。合成回复与 API 错误消息不计作有效样本。有限检查点保留最近 64 个消息及 256 个父链节点，以支持交错片段和增量续读。
- **生成速度**：有明确首字计时，且本地记录没有推理 Token 时，以输出 Token /（总耗时 − 首字等待）计算。通用有效生成窗口至少 100 ms，速度不超过 10,000 tok/s；Codex 单调用轮次的日志额外要求生成窗口至少 1 秒、输出至少 100 Token，排除末尾一次推送造成的假高速。本地日志没有首文本或流速证据，有推理 Token 时不把全部输出算作已测得生成速度。
- **速度下限 `≥`**：不具备生成速度样本时，Codex 有推理 Token、回答部分至少 100 Token 且首字后窗口至少 1 秒，可用（输出 − 推理 Token）/ 首字后窗口提供回答速度下限。否则，Codex、Claude Code 等已支持来源只有输出至少 1,000 Token、整次耗时至少 1 秒且所得速度不超过 10,000 tok/s，才提供 输出 / 整次耗时 的保守下限。同一条请求不会同时计入生成速度与速度下限。
- 生成速度和速度下限分别加权汇总、分别统计样本数；首字计时有效但速度证据不足时，仍计入首字均值。短输出或计时证据不足时保持未知，不通过调整门槛伪造速度样本。以上规则针对 CLI 日志；网关来源另外使用直接观察到的首文本、可见推理与流式突发证据，详见[网关指标](gateway.md)。
- 归档复制按稳定请求身份合并，不使用时间窗口去重。Codex 派生会话中继承的旧事件不计作新请求。缺少时序证据时保持未知。

## 性能边界

只在弹窗打开期间采集当前绑定目录，关闭即取消；弹窗内每 5 秒检查增量，不因首页切换 Provider 触发全量扫描，也不为此请求模型、余额或推理接口。先展示已有索引，再在后台补齐历史。首次索引大量日志可能分多批完成，界面会标记未完成。

索引位于 `$XDG_DATA_HOME/usage/performance.sqlite3`，未设置时为 `~/.local/share/usage/performance.sqlite3`。独立 SQLite WAL 表按来源格式版本、Agent、规范化 Home 隔离；同一 Home 共用游标，不加载全量 Token 历史。

- 每批正文读取上限 4 MiB，并在读取循环中检查 100 ms 软预算和取消信号；预算不保证磁盘操作或 SQLite 提交的硬超时。批间让出执行，终端线程不解析日志。
- 每批最多发现 256 个目录项，目录递归深度最多 16。已发现文件按游标轮询 64 个，并优先检查最近活跃的 8 个。目录发现完成后每 30 秒重查，`r` 可提前重查；大量历史文件下，发现旧文件新追加可能有轮询延迟。
- 每行最多缓冲 1 MiB，更长行流式跳过并计数。未完成的尾行等待追加，不在每次刷新时重复读；文件未变更时仅检查元数据，正文读取为 0。追加时核对边界摘要并读取新增部分。
- 游标、有限解析状态和请求记录同事务保存，重启继续增量。旧解析格式会在打开详情后按批重读一次，沿用稳定请求身份，保留已索引但源文件已删除的历史。文件替换或截断后重读，稳定请求 ID 避免重复计数；删除源文件保留已索引历史。
- 支持 `.jsonl.zst` 归档，与同名 `.jsonl` 共用逻辑身份；两者同时存在时优先普通文件，避免读取压缩中的半成品。压缩日志在内存中流式解码，同样受每批 4 MiB、每行 1 MiB 和取消检查约束，不生成解压临时文件。同一绑定的连续批次保留一个解码器；重启或切换绑定后，未完成归档从头分批重放，稳定请求 ID 保证幂等。已完成且未变化的归档不重读正文。
- 指标在后台通过 SQL 聚合，明细分页读取，不把全部历史请求载入界面。大范围聚合仍随有效请求量增长，首次导入和统计不是零开销。

索引保留时间、模型、请求身份、Token 与时序等元数据，不保存对话、思考原文、工具正文或认证信息。边界校验只存 SHA-256 摘要。索引目录权限为 700，数据库为 600。当前不自动删除历史索引；长期常驻或超大规模分析可进一步增加保留策略及滚动聚合。

## 扩展与验证

`AgentAdapter::request_source()` 提供可选的 `RequestSource` 工厂，负责目录范围、事件解析和有限检查点；`performance::Service` 负责增量采集与查询。`Hub::Provider::performance_binding()` 和首页目录使用同一绑定模型；`Provider::performance()` 读取已建立的索引。读取和刷新均为同步存储操作，调用者应像会话扫描一样在后台执行。新增来源不需要修改首页按键或指标聚合逻辑。

交互式加载使用 `Service::start_load`：调用者传入固定的 `LoadRequest`，接收缓存、进度和结束结果，并持有 `LoadTask` 管理取消。批次调度、进度节流、异常收尾和取消检查由服务层负责；弹窗关闭、翻页或更换时间范围时丢弃旧任务，并用界面代次拒绝迟到结果。

测试使用合成日志和临时数据库，覆盖追加、重启、归档复制、文件替换、尾行、大行、派生会话、提供方隔离、片段合并、缺失时序、首字均值、生成速度与速度下限的独立加权、Magpie 边界案例、旧游标升级、万条请求，以及弹窗后台加载和过期结果丢弃。没有主动发送真实模型请求校准日志估算。

参考实现：Magpie `internal/usage/usage.go` 的 `DecodeWindow`、`MeanTTFT`，`internal/usage/ledger.go` 的 `Row.Decode` / `Row.Floor`，以及 `internal/usage/speed_count_test.go` 的本地 Codex / Claude 样例。本项目将同一套 SQL 计量规则用于首页、模型汇总和请求明细，直接重新聚合原有索引；旧索引中的推算首字不再作为有效首字样本。

本轮对齐验证：25 组 Magpie 本地日志规则案例及历史游标重读、归档和删除源文件后的历史保留、延迟用量记录、宽窄屏展示均通过；全量 333 项 Rust 测试串行通过，Clippy 全 target、格式与差异检查通过。仅只读核对现有索引，未为验证发送推理请求。
