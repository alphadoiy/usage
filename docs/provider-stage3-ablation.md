两项结构优化对照均通过原有 242 项测试，补充探针无新增失败。嵌套命令修复对照通过原有 242 项和全部 12 项补充探针；这个修复仅发生在实验副本中。

本次仅新增实验脚本、探针和报告，没有修改生产实现或原有测试。全部实验在一次性副本进行，输入文件的 SHA-256 清单用于确认工作区源码、Cargo 文件和原测试前后一致。

## 已复现的解析缺口

位置：[effective.rs](../src/codex_manager/effective.rs)，`positional` 仅区分第一个位置参数。

```text
usage codex run <账号> -- exec resume <会话 UUID>
usage codex run <账号> -- exec review "review this change"
```

当前两个探针都观察到 `context.identity.state = resolved`，契约预期为 `unresolved`。解析器遇到 `exec` 后将 `positional` 设为 true，后续 `resume` / `review` 不再经过子命令门控。独立的恢复参数和根命令 `resume` 已被防护，嵌套形式却绕过了同一策略。

影响是：即使配置来源尚未支持，也可能保存 `matched` 资源关联，并允许 `resources --run` 沿用启动侧推断。测试使用模拟 Codex，证明的是启动器错误宣称已解析；没有证明真实恢复会话必定切换到另一账号或实际发生错误扣费。

官方文档明确支持 [`codex exec resume`](https://learn.chatgpt.com/docs/developer-commands?surface=cli)。本机离线执行 `codex exec --help` 也列出 `resume`、`fork`、`review`；本轮失败探针直接覆盖 resume 与 review，fork 具有相同静态解析路径，但没有单独计作第三个已复现探针。

修复时应识别命令层级，并保留提示词边界。补充正向探针确认 `exec "resume the migration"` 和 `-- resume` 仍应正常解析，不能改成扫描所有参数中是否出现关键词。实验修复对照仅在副本中实现这一门控，不代表已经实现完整 Codex 参数语法或真实 Agent 配置确认。

## 哪些机制不是冗余

1. **推理配置进入版本摘要。** 仅移除 `inference` 的摘要输入，原测试仍通过；修改推理端点后旧运行关联未失效，补充探针失败。资源查询地址与推理地址是不同信息，不能用前者代替后者。
2. **当前账号关联复核。** `profile_ids` 不在配置版本摘要中，启动时筛选和查询时复核负责不同时间点。删除关联后仍可查旧运行，是移除复核后的可观测变化。
3. **查询凭据固定。** 校验后返回专属 resolver，才能让后续 HTTP 使用同一份凭据。把 resolver 换回环境读取，新增单元探针取不到之前已验证的合成值。探针通过依赖注入区分两个来源，不依赖不安全的并发环境变量修改，也没有模拟实际网络请求期间的密钥轮换。
4. **运行记录事务。** 对 `run_contexts` 注入插入失败后，应没有残留 Run。移除事务会留下孤立运行，新增故障注入探针能发现。
5. **资源工厂验证。** 启动时工厂校验阻止未知服务被记成 `matched`。后续查询工厂可能仍拒绝执行，但首页若使用该匹配状态会得到错误元数据，不能仅靠查询阶段兜底。
6. **看似重复的一致性检查。** 服务类型已进入版本摘要，身份未解析通常也不会产生匹配链接；但这些检查还能拒绝持久化上下文内部不一致。私有探针故意修改已捕获元数据后验证拒绝行为。它们不是正常用户路径的证明，也不是密码学完整性保证，但足以反驳“完全没有作用”的判断；当前没有必要为了少一次比较而删除。

`remove_child_env_pinning` 若保持全绿，只表示本轮输入没有区分“读取后显式注入”与“稍后由子进程继承”；没有覆盖两者之间进程环境被改变的场景。该机制与查询 resolver 固定发生在不同边界，不能据此合并或删除。

## 可收敛的结构

### 合并运行上下文读取

`Manager::resources_for_run` 先调用 `run_record`，读取并反序列化完整上下文，随后再次 SELECT 同一 `context_json` 并反序列化私有上下文。查询实际只需要 `profile_id` 和私有 `CapturedContext`。

实验变体把它合并为一次 LEFT JOIN 和一次反序列化，保留未知运行、旧运行和关联校验错误。这是明确的重复工作，可以用私有仓储读取方法收敛，不需要增加全局缓存。

### 延迟资源服务构造

启动捕获无条件创建内置资源注册表和 `ResourceService`，后者立即创建 Reqwest 客户端。没有候选资源时，捕获不会调用工厂，但客户端仍已构造。

实验使用局部 `OnceCell` 延迟到第一次需要工厂时构造服务，保留原工厂校验。它避免无候选资源时的构造；本轮没有测真实启动延迟，不将编译／测试耗时当作性能收益。后续还可把静态资源规格校验与 HTTP 查询上下文分离，但不应退化成只检查服务名称。

### 其他静态维护问题

- `CapturedContext` 将 `resources` 与 `proofs` 保存为平行数组，靠下标对齐。可改为内部 `CapturedLink { link, proof }`，对 CLI 再投影公开字段，降低以后筛选或排序时的错位风险；当前没有复现错位缺陷。
- 捕获只需要资源配置，却调用完整 `load_config`；其数据目录校验还会读取托管 homes。应拆分配置解析与账号发现，或由应用入口传入已校验配置，避免扩大 Manager 对 UI 配置和数据发现的依赖。
- CLI 已打开的 Manager 与 Agent 适配器再次打开 Manager 是既有重复。独立日志计数探针观察到一次 CLI 启动有 2 个 `codex.manager_open` 事件；探针使用嵌套命令修复对照的编译产物，该变体未改 Manager 打开路径，证据在实验目录 `manager-open-metric.log`。新增捕获还涉及配置读取；不能把静态读取到的每个 SQLite 连接都记成一个 `codex.manager_open` 日志事件。
- `resolved` 仍是启动器支持范围内的推断，不是 Agent 确认。应保留这个边界，避免在首页直接写成“当前实际使用”，并继续将会话、进程存活、交互内切换列为后续能力。

## 建议顺序

1. 修复嵌套命令门控，并将两个失败探针及普通提示词正向探针迁入正常回归。
2. 把推理配置变更、移除账号关联、凭据固定、事务失败和未知工厂探针迁入正常回归。原有安全校验不应因为消融仍全绿而删掉。
3. 合并上下文读取，延迟服务构造，收敛内部捕获结构及配置加载边界；保持公开 CLI JSON 与旧运行兼容。
4. 再将首页接到 Provider / Run / ResourceSnapshot；启动关联先可靠，首页才有可信的数据基础。
