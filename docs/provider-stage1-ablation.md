# 第一阶段架构评估与全项目消融（2026-10-15）

> 以下保留优化前的实验输入和结果。四个失败契约已经修复，详见 [第一阶段优化记录](provider-stage1-optimization.md)。当前脚本会运行迁入正常 Cargo 测试的回归，不再注入历史失败探针。

## 结论

第一阶段的拆分方向可以保留，但还不能视为完成了“Provider 中枢”。已验证的现有行为收益是缓存作用域隔离、注册冲突检查和可扩展会话 ID 校验；Hub、资源接口目前主要提供后续扩展入口。旧查询链和新资源链之间存在可简化的往返包装，账号身份也还没有贯穿 UI、提醒和会话恢复。

建议先收尾第一阶段，再接实际 BYOK 接口。否则第二阶段会把多账号数据接到仍按工具类型区分状态的界面和提醒上。

本次没有修改现有生产实现和原测试断言，只新增实验脚本、探针和报告。源码/Cargo/原测试文件的 SHA-256 清单确认实验前后一致。

## 方法与覆盖范围

在 `/private/tmp/usage-stage1-ablation-20261015` 使用同一份未提交源码快照。每个变体恢复源码后只修改一个目标因素，运行完整 `cargo test --offline --quiet --no-fail-fast -- --test-threads=1`。没有删除测试或放宽断言。源代码副本、编译产物、账号存储与日志目录均和工作区隔离；APFS 克隆原 target 仅用于复用依赖编译缓存。

基线包含原来的 218 个测试，另加 1 个正向行为探针，共 219 项。新增正向探针使用真正的内置 Codex 工厂、两个合成 Home、不同的模拟 HTTP 响应和同一个缓存文件，验证账号 B 不会拿到账号 A 的结果，而不是仅比较两个哈希是否不同。

完整回归覆盖官方用量解析、凭据处理、账号配置与导入、并发运行与 OAuth 租约、Bark、结构化日志、历史账本、会话扫描/恢复、无真实终端的 UI 测试及 CLI。额外选择查询超时、UI 代际检查、Bark 来源门控和历史增量读取作为跨模块消融对照。它们是原有机制，不是本轮新引入的改动。

四个新边界探针单独运行，不混入应当全绿的回归基线。这些探针用于检验下一阶段所需契约，允许失败并保留失败证据。它们失败不表示现有单账号 CLI 的四项功能都已发生回归。

## 消融结果

| 变体 | 通过 / 失败 | 观察与判断 |
| --- | --- | --- |

| 启动绕过 Hub/Agent 包装，直接调用 Manager | 219 / 0 | 当前启动包装没有提供新增的受测运行语义；这是保留扩展点的理由评估，不是必须删除注册表的证据 |
| 展平旧用量到资源再返回旧用量的包装，保留缓存身份与重置委托 | 219 / 0 | 现有额度查询不依赖这条往返链，可以采用更薄的兼容边界 |
| 内置会话恢复为固定 loader 列表 | 219 / 0 | 当前三个内置来源的行为相同；自定义注册表测试仍保留，不能由此否定扩展能力 |
| 重复类型注册改为覆盖 | 218 / 1（复测） | 注册冲突契约失败，保留显式拒绝 |
| 内置资源缓存键退回工具 ID | 217 / 2 | 原身份测试和新的真实查询探针均失败；账号 B 读到 A 的 20%，预期是 B 的 80% |

| 移除通用查询超时 | 217 / 2 | 查询取消和阻塞凭据读取的截止时间测试失败，保留截止时间保护 |

最后一项是分步对照：先绕过 Hub，观察仍打开两次，再由 CLI 复用已有 Manager，观察只打开一次。它不证明“复用 Manager”和“保留完整 Hub”必然冲突；后续应通过依赖注入同时做到。

允许重复注册的首轮结果为 217 / 2，除预期的注册冲突断言外，一个已有 HTTP 模拟服务读取请求时发生 `WouldBlock` 超时。完整复测得到 218 / 1，仅注册断言失败。该额外失败不归因于注册表改动，两轮日志均保留。Bark 的一个日志测试还会启动精确筛选的子测试；汇总已排除失败输出中的嵌套摘要，避免重复计算测试数量。

## 新边界探针：四个缺口均复现

| 优先级 | 探针与结果 | 根因与影响 |
| --- | --- | --- |
| 多账号接入前修复 | 两个 Codex 账号分别回传 a/b，卡片结果实际为 `[b, 空]`，预期 `[a, b]` | [刷新事件](../src/ui/app.rs) 与卡片匹配使用工具 ID，第二个结果仍写进第一张卡。缓存键的隔离尚未传递到 UI 身份 |
| 多账号接入前修复 | 两个无邮箱账号都达到低额度，A 产生 1 条提醒，B 为 0 | [QuotaMonitor](../src/alerts.rs) 按工具、邮箱、窗口保存状态；无邮箱或相同邮箱的不同资源账号共用状态 |

四项探针均完整复测，结果稳定为 0 通过 / 4 失败。输入全部是合成数据和本地命令；这里的资源故障探针专门测试任务 panic。

## 全项目结构评估

### 可以保留的基础

- 现有 HTTP、时间与 Keychain 注入，合成测试能力，以及账号保存版本和乐观并发控制，继续提供明确的测试边界。
- Agent 与资源服务两条扩展轴符合需求；增加一个余额服务不应要求它伪造 quota 百分比，增加 Agent 也不应复制全部账单逻辑。
- 工厂和注册表只负责构造；显式拒绝冲突、按配置顺序返回结果，属于小而明确的约定。
- 原有查询截止时间、UI 代际检查、历史增量读取、OAuth 隔离与 Bark 来源过滤都应保留。后两项相关完整回归在结构简化变体中继续通过；本次没有逐项消融所有 OAuth/Bark 安全机制。

### 尚未完成的职责分离

1. **Hub 还不是所有业务路径的应用服务。** 实际启动 helper 每次创建 `Hub::default()` 和内置注册表；外部注入的注册表没有由应用入口一直传入。`Provider::resources()`、`Provider::sessions()` 的当前调用点都在测试中，不能把“启动经过 Hub”解释为查询、运行、会话已经形成闭环。
2. **旧资源查询存在往返包装。** 当前路径是 `ProviderFactory → ResourceRegistry → SubscriptionResource → LegacyUsageAdapter → 原 UsageProvider`，而 LegacyUsageAdapter 最终直接查询原对象，跳过 typed `read()` 转换。消融证实旧额度输出并不需要整条链；应让兼容层位于输出边界，并给新资源读取器增加真实应用消费者。
3. **仍有双向模块依赖。** `agents` 引用 `sessions` 的记录/loader，`sessions` 又引用 `agents`；`providers` 构建 `resources`，`resources` 依赖旧 provider 接口。原来的 `config → codex_manager → config` 也未消除。Rust 能编译这些引用，不等于领域边界已经解耦。
4. **公共运行类型仍绑定 Codex。** `AgentContext::ManagedCodex` 与 `SpawnOutcome.run: Option<codex_manager::RunRecord>` 让通用接口认识具体实现。应把通用运行身份和能力放到独立模型/端口，再由 Codex 适配器实现保存和启动细节。
5. **配置、发现和历史来源仍是旧结构。** `AppConfig::data_instances()` 打开托管存储且忽略发现错误；实例来源校验及历史目录/解析仍限定三个工具。新增一个 Agent 目前不能仅靠注册就贯穿所有功能。历史能力可以可选，但未支持时应明确表达。
6. **spawn 仍同步等待退出。** 当前工作流保持兼容，但没有可立即返回、供中枢查询或控制的运行句柄；RunRecord 也没有处理进程存活核对、全部 CLI 覆盖或 Run 到新会话的关联。这些边界在原迁移文档中已注明，本轮没有证明它们已实现。

第一阶段的 `src` 从 HEAD 的 22,558 行增至 23,763 行，净增 1,205 行，含测试、空行和注释。该数字只表明增加了维护面，不是性能或复杂度评分。当前更值得减少的是重复的调用路径和具体实现耦合，而不是把小注册表换成哈希表或增加全局缓存。

## 推荐收尾顺序

1. **统一身份。** 引入明确的资源/查询目标身份，贯穿刷新事件、卡片、缓存、重置选择和提醒；不要继续使用邮箱或工具名代替账号身份。将本次两个身份探针转为正式回归。
2. **贯通启动和恢复。** 在应用入口组装并传递 Hub；复用已打开的账号仓储/运行服务，避免重复打开 Manager。恢复会话也使用对应 Agent 的 Launcher，保留 Home/账号绑定；运行元数据移出 Codex 私有模块。
3. **收敛资源边界。** 逐项处理资源任务错误，保留正常结果；明确一个截止时间的负责层。将旧用量兼容移到边界，避免靠双向包装维持两套查询入口。
4. **再接真实资源服务。** 配置资源连接和凭据引用，接 New API/官方 API，并加入真实的资源查询命令。随后再迁移首页，才能让抽象与实际数据闭环。
